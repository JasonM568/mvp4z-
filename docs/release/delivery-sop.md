# 交付作業標準（每一項改動都照這個走）

2026-10-23 使用者指出：同一輪工作裡一下跑本機、一下開瀏覽器、一下直接查資料庫，做法沒有標準，
結果是「改了卻沒上線」「上線了卻沒親眼看過」「驗收方式每次不同」。以下為固定流程，不因為改動大小而省略。

## 一、動手前（每次）
1. 讀 `handoff.md`、`worklog.md` 最新紀錄、`git status`、`git rev-list --count origin/main..HEAD`。
2. 要推送前：未推送 commit 數必須等於這次要推的數量；`git diff --stat origin/main..HEAD -- supabase/migrations` 有新 migration 就先處理資料庫。
3. 改動範圍不明或會動到正式資料／付款／點數：先說明再做，不邊做邊猜。

## 二、驗證（固定四關，順序不變）
1. **型別與單元測試**：`npx tsc --noEmit`、`npx vitest run`，全綠才往下。
2. **畫面驗證只用 ego lite**（`ego-browser`），不用其他方式替代：
   - 手機尺寸（390×844）與桌機各看一次；看實際截圖，不只看 DOM 文字。
   - 需要會員登入時，請使用者在 ego lite 登入後說「繼續」；不替使用者輸入帳密。
   - 不為了省事另外寫臨時預覽頁；真的需要時，測完立刻刪除，且不得進入 commit。
3. **提交與推送**：只 `git add` 這次的檔案；commit 訊息寫為什麼；推送後用 Vercel 確認部署 `READY`。
4. **上線後驗收**：在 `www.xunfeng.tw` 用 ego lite 重做第 2 關的關鍵步驟；有扣點或寫入正式資料的測試，用管理員測試帳號並在回報中寫明。

## 三、資料庫
- migration 先在 repo 寫好，再逐支套到正式庫並用查詢驗證；套用順序與 Vercel 上線順序必須同步（先資料庫、後程式）。
- 不用 `drop`／刪除既有資料，除非使用者明說；改資料前把舊值寫進 `admin_audit_logs`。

## 四、回報格式
每次回報固定三段：**做了什麼**、**怎麼驗證的（附實際結果）**、**還沒做／有風險**。沒親眼驗證過的，明寫「未驗證」。

## 五、紀錄
- 每完成一項就更新 `worklog.md`；收工再更新 `handoff.md`。
- 使用者提出的流程問題，寫進本文件，不只回「下次注意」。
